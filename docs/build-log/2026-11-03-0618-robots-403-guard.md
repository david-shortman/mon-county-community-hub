# A 403 on robots.txt no longer means "read anything"

**What:** The shared robots.txt check (`site/src/lib/robots.mjs`) now treats only a 404 or 410 as "no robots.txt". A 403, 429 or other refusal, a server error, or a web page sent in place of a robots.txt means nothing on that site is read in that run. Each read tries 3 times, a second apart. The daily Source check now checks robots.txt again before following each redirect.

**Why:** Running `npm run update-feeds` saved a "live" copy of the City of Morgantown calendar feed, which the City's robots.txt blocks. The City's server sends a 403 page for some reads of its robots.txt, and the old code read a 4xx as permission. David chose to keep robots rules strict, so an unclear answer now means no.

**Tests:** `site/test/robots.test.mjs` checks every kind of robots.txt answer, that a blocked feed is never requested or saved as live, and that the Source check never follows a redirect into a blocked path. The new tests fail on the old code.

**Trade-off:** on a run where the City answers every try with 403 or 503, nothing on the City site is read (meetings, City page watches). They use their saved copy and try again the next run. Details: `docs/operations/automated-reads.md`, "What changed on 2026-11-03". Sprint wave 13, #529.
